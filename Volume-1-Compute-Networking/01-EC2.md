> # 1. Business Problem
>
> Before cloud computing, companies purchased physical servers.
>
> Problems:
>
> - High upfront cost
> - Weeks to procure hardware
> - Difficult scaling
> - Hardware failures
> - Manual maintenance
> - Low utilization
>
> Example:
>
> A company launches an e-commerce website.
>
> Initially:
>
> ```
> 500 users/day
> ```
>
> During Diwali Sale:
>
> ```
> 200,000 users/day
> ```
>
> Buying servers for peak traffic means expensive hardware sits idle for most of the year.
>
> AWS solved this problem by introducing **Amazon EC2**, allowing users to provision virtual servers within minutes and pay only for what they use.
>
> ---
>
> # 2. What is Amazon EC2?
>
> Amazon EC2 (Elastic Compute Cloud) is a service that provides resizable virtual machines in the cloud.
>
> EC2 allows developers to:
>
> - Launch virtual servers in minutes.
> - Scale up or down based on demand.
> - Pay only for consumed resources.
> - Choose CPU, memory, storage, operating system, and networking.
>
> Think of EC2 as renting a virtual server instead of purchasing a physical server.
>

> # 3. Key Components
>
> ## Instance
>
> A running virtual machine.
>
> Example:
>
> ```
> Production Web Server
> Jenkins Server
> SonarQube Server
> Bastion Host
> ```
>
> ---
>
> ## AMI (Amazon Machine Image)
>
> Blueprint used to launch EC2.
>
> Contains:
>
> - Operating System
> - Installed Software
> - Packages
> - Configuration
>
> Example:
>
> Ubuntu + Java + Tomcat
>
> Every EC2 launches from an AMI.
>
> ---
>
> ## Instance Type
>
> Determines:
>
> - CPU
> - Memory
> - Network Performance
> - Storage Capability
>
> Examples:
>
> ```
> t3.micro
> t3.medium
> m6i.large
> c6i.large
> r6g.large
> ```
>
> ---
>
> ## EBS Volume
>
> Persistent block storage attached to EC2.
>
> Stores:
>
> - OS
> - Application
> - Logs
> - Configuration
>
> (Covered in the next chapter.)
>
> ---
>
> ## Security Group
>
> Acts as a virtual firewall.
>
> Controls:
>
> - Incoming traffic
> - Outgoing traffic
>
> Example:
>
> ```
> Allow SSH (22)
> Allow HTTPS (443)
> Allow HTTP (80)
> ```
>
> ---
>
> ## Key Pair
>
> Used for SSH authentication.
>
> AWS stores:
>
> Public Key
>
> User stores:
>
> Private Key (.pem)
>

> # 4. Internal Working
>
> ```
> User
>      │
>      ▼
> AWS Console / CLI
>      │
>      ▼
> Launch Instance
>      │
>      ▼
> AMI Selected
>      │
>      ▼
> Instance Type Selected
>      │
>      ▼
> Security Group
>      │
>      ▼
> EBS Attached
>      │
>      ▼
> Hypervisor
>      │
>      ▼
> Physical Host
> ```
>
> AWS virtualizes physical hardware using a hypervisor (Nitro System in modern instances), allowing multiple isolated EC2 instances to run securely on the same physical infrastructure.
>

> # 5. EC2 Launch Flow
>
> ```
> User
> ↓

> # 8. Production Scenarios
>
> ## Scenario 1
>
> Users report that the application is slow.
>
> Investigation:
>
> ```
> CloudWatch
> ↓
> CPU
> ↓
> Memory
> ↓
> Disk
> ↓
> Network
> ↓
> Application Logs
> ```
>
> ---
>
> ## Scenario 2
>
> EC2 Status Check Failed.
>
> Possible Reasons:
>
> - Hardware issue
> - OS kernel panic
> - File system corruption
> - Network issue
>
> Resolution:
>
> - Review System Status Checks
> - Check EC2 Console Output
> - Recover or replace the instance if necessary
>
> ---
>
> ## Scenario 3
>
> SSH Connection Failed.
>
> Check:
>
> - Instance running?
> - Security Group allows port 22?
> - Correct Key Pair?
> - NACL allows traffic?
> - Route Table?
> - Public IP attached?
>

> # 9. Troubleshooting Playbook
>
> ## Problem
>
> Cannot SSH into EC2.
>
> Investigation Flow:
>
> ```
> EC2 Running?
> ↓
> Public IP?
> ↓
> Security Group
> ↓
> NACL
> ↓
> Route Table
> ↓
> Internet Gateway
> ↓
> Correct PEM File
> ↓
> SSH Command
> ```
>
> ---
>
> ## Problem
>
> CPU = 100%
>
> Investigation:
>
> ```
> CloudWatch
> ↓
> top
> ↓
> htop
> ↓
> ps
> ↓
> Application Logs
> ↓
> Database
> ```
>
> Commands:
>
> ```bash
> top
> htop
> ps -ef
> vmstat
> iostat
> free -h
> df -h
> ```

>

>
> ```bash
> aws ec2 describe-instances
> ```
>

>
> ```bash
> aws ec2 start-instances --instance-ids i-xxxxxxxx

>
> Stop instance:
>
> ```bash
> aws ec2 stop-instances --instance-ids i-xxxxxxxx
> ```
>
> Reboot:
>
> ```bash
> aws ec2 reboot-instances --instance-ids i-xxxxxxxx
> ```
>
> Describe instance status:
>
> ```bash
> aws ec2 describe-instance-status
> ```

> # 11. Best Practices
>
> - Use IAM Roles instead of Access Keys.
> - Use Security Groups with least privilege.
> - Enable CloudWatch monitoring.
> - Keep AMIs updated.
> - Use Auto Scaling for production workloads.
> - Encrypt EBS volumes.
> - Use Systems Manager instead of opening SSH where possible.

> # 15. Common Mistakes
>
> ❌ Opening SSH (22) to `0.0.0.0/0` in production.
>
> ❌ Hardcoding AWS Access Keys on the instance.
>
> ❌ Ignoring EC2 Status Checks.
>
> ❌ Not enabling monitoring or logging.
>
> ❌ Using the root user for application deployment.
>
> ❌ Creating oversized instances without analyzing CPU and memory utilization.
